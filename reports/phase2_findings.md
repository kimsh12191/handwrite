# Phase 2 — 실제 variation 측정 결과

측정 대상은 HangulDB PE92 train(2,350 클래스 × ~81장, 188,465장)과
SERI95 test(520 클래스 × ~100장, 51,785장)이다. 둘은 1992년과 1995년에
서로 다른 기관이 수집한 별개 코퍼스이므로, 아래 수치는 모두 **두 코퍼스에서
독립적으로 재현되는지**를 같이 적는다.

재현 방법은 이 문서 맨 아래에 있다.

---

## 요약 — 이번 측정이 바꾸는 결정

| # | 측정된 것 | renderer 설계에 대한 함의 |
|---|---|---|
| 1 | 클래스 내부 variation이 요약통계 11차원 PCA에서 분해되지 않는다 (PC1 23%) | Phase 2를 요약통계로 하면 taxonomy 근거가 안 나온다. 기저를 바꿔야 한다 |
| 2 | 공간 기저에서도 80% 분산에 중앙값 28개 성분이 필요하다 (PC1 11%) | 한 음절 클래스의 자유도가 전역 파라미터 몇 개로 덮이지 않는다 |
| 3 | **선언된 4-DOF 합성군은 같은 척도에서 4개 성분으로 측정된다** | 위 28이라는 수는 기저 아티팩트가 아니라 실제 신호다 |
| 4 | 종성 context 효과의 68%가 수직 압축 1개로 설명된다. 나머지 32%는 남는다 | 음절 층에 packing 파라미터 1개가 필요하되, 그것만으로는 부족하다 |
| 5 | 압축 계수가 중성 부류별로 갈린다 (horizontal 0.67 < vertical 0.71 < mixed 0.78) | packing이 상수가 아니라 중성 부류의 함수다 |

가장 중요한 것은 **3번**이다. 3번이 없으면 2번은 "픽셀 PCA는 원래 잘 안 된다"와
구분되지 않고, 그 위에 세운 taxonomy는 전부 근거가 없다.

---

## 1. 요약통계 PCA는 해석 가능한 축을 주지 않는다

`scripts/pca_report.py`를 SERI95 520클래스에 돌린 결과다.
README/USER_GUIDE가 예시로 든 모양은 이랬다.

```text
PC1 aspect          42%
PC2 rotation        21%
PC3 asymmetry       15%
PC4 compactness      9%
```

실제로 나온 것은 이렇다 (520클래스 평균).

```text
PC1 22.8%   PC2 17.9%   PC3 14.2%   PC4 10.8%   PC5 8.8%
```

스펙트럼이 완만하게 내려가고 지배적인 축이 없다. loading도 한 축에 4개 이상
섞인다. 예를 들어 `가`의 PC1은

```text
area_ratio +0.49, compactness -0.46, lr_asym -0.46, aspect +0.39
```

이라서 "이 축은 X다"라고 이름 붙일 수가 없다. USER_GUIDE §7이 상정한
"PCA 결과를 읽고 그 자유도를 renderer에 넣는다"는 절차가 이 기저에서는
성립하지 않는다.

이유는 구조적이다. 이 11개 feature는 전부 **음절 전체의 요약값**이다.
`각`에서 초성 ㄱ만 커지는 변화와 종성 ㄱ만 커지는 변화가 aspect·compactness에
거의 같은 방향으로 들어간다. 국소적인 변화가 전역 통계에서 섞인다.

→ 산출물: `reports/seri95_pca.json`

## 2. 공간 기저로 바꿔도 성분 수가 줄지 않는다

`scripts/shape_space.py`는 같은 질문을 공간적으로 분해된 기저에서 다시 던진다.
각 샘플을 bounding box로 자르고 24×24 잉크 밀도맵으로 리샘플한 뒤 클래스별 PCA를
한다.

| 코퍼스 | 클래스 | 80% 분산에 필요한 성분 (min/중앙/max) | 90% | PC1 평균 |
|---|---|---|---|---|
| SERI95 | 120 | 18 / **28** / 34 | 31 / 43 / 50 | 11.5% |
| PE92 | 300 | 19 / **29** / 34 | 31 / 43 / 48 | 9.6% |

두 코퍼스가 거의 같은 값을 준다. 클래스당 샘플이 100장인데 90% 분산에 43개
성분이 필요하다는 것은, 이 기저에서 데이터가 사실상 압축되지 않는다는 뜻이다.

PC 모드를 그림으로 보면 이유가 드러난다 (`reports/modes/seri95/*.png`,
맨 왼쪽이 평균, 이후 PC1~PC4를 빨강/파랑 부호로 표시).
상위 성분이 전부 **획의 양옆에 빨강-파랑이 짝지어 나타나는 형태**다.
`동`처럼 ㅇ이 있는 음절에서는 ㅇ 둘레에 동심원 형태의 빨강-파랑 띠가 나온다.
이것은 모양이 바뀌는 모드가 아니라 획이 조금씩 어긋나는 모드다.
즉 상위 분산이 형태가 아니라 **정합(registration)** 에 쓰이고 있다.

여기서 한 가지를 구분해야 한다. 샘플은 이미 bounding box로 잘려 정규화되므로
**전역 평행이동과 전역 크기는 이미 제거된 상태**다. 그런데도 정합 모드가 상위를
차지한다는 것은, 남은 어긋남이 글자 전체의 이동이 아니라 **구성요소들의 상대
위치가 흔들리는 것**이라는 뜻이다. `동`의 예에서 ㅗ의 가로획 높이와 ㅇ의 크기가
따로 논다. 이것은 4절에서 종성 압축이 실제로 측정되는 것과 같은 방향의 증거이고,
taxonomy에서 packing을 음절 층 파라미터로 두어야 하는 이유이기도 하다.

## 3. 그래서 척도를 먼저 검증한다 — 이 측정은 저차원을 저차원으로 읽는가

2번만 보면 두 가지 해석이 가능하고 둘은 정반대 결론을 준다.

- (A) 손글씨의 클래스 내 자유도가 실제로 높다
- (B) 픽셀 기저가 나빠서 무엇을 넣어도 성분 수가 커진다

(B)라면 28이라는 수로는 아무 파라미터도 정당화할 수 없다. 그래서
`scripts/basis_control.py`가 **자유도를 아는 합성군**을 만들어 같은 측정을 건다.
실제 샘플 1장에서 회전/전단/이방성 스케일/획 굵기만 흔들어 100장을 만들고,
real 데이터와 똑같은 bbox 정규화·리샘플·PCA를 통과시킨다.

| 합성군 | 선언 DOF | 80% 분산 성분 | 90% | PC1 |
|---|---|---|---|---|
| 회전만 | 1 | **2** | 3 | 63.9% |
| 회전+전단 | 2 | **4** | 6 | 41.8% |
| 회전+전단+이방성 스케일 | 4 | **4** | 6 | 40.6% |
| + 획 굵기 | 5 | **5** | 7 | 41.4% |
| **실제 SERI95 클래스** | — | **28** | 43 | 11.5% |

PE92 샘플로 만든 합성군도 같다 (1-DOF→2, 2-DOF→4, 4-DOF→5, 5-DOF→5).
`reports/seri95_basis_control.json`, `reports/pe92_basis_control.json`.

척도는 저차원 족을 저차원으로 정확히 읽는다. 따라서 (B)는 기각되고 28은 실제
신호다.

**이것이 이번 단계의 핵심 결과다.** 전역 affine + 굵기 — 즉 "전역 style
파라미터를 흔든다"는 접근 전체 — 는 이 척도에서 4~5차원으로 측정되는데,
같은 척도에서 실제 한 클래스 내부 변동은 28차원이다. 부족한 자유도는 음절
아래층, 즉 자모/획 단위에 있을 수밖에 없다.

HANDOFF §1의 질문 `I_ref ∈ {R(θ)}?` 에 대해, **전역 파라미터만 가진 renderer
군에 한해서는 답이 "아니오"**라는 것이 측정으로 확인된 셈이다.

주의: 28은 상한이다. 픽셀 기저는 정합에 분산을 쓰므로 실제 형태 자유도는 이보다
작다. 이 수를 "renderer에 파라미터 28개가 필요하다"로 읽으면 안 된다.
읽는 방식은 "전역 4~5개로는 확실히 모자라다"이다.

## 4. 종성 context 효과 — 압축 하나로 얼마나 설명되는가

HANDOFF §5는 같은 자모라도 역할이 다르면 모양이 다를 수 있으니 동일 분포를
가정하지 말라고 한다. 이것은 설계 결정을 가른다.

- 압축 1개로 설명된다 → 음절 층에 packing 파라미터 하나 추가
- 설명되지 않는다 → 자모 shape을 역할별로 따로 가져야 한다

`scripts/jamo_context.py`가 이것을 잰다. (초성, 중성)이 같고 종성 유무만 다른
클래스 쌍을 모아, 열린 음절의 평균 잉크맵을 위쪽 f 비율로 눌러 넣었을 때
닫힌 음절의 위쪽 f 영역과 얼마나 맞는지 코사인으로 본다. f는 스윕해서 최적값을
쓴다.

기준선 두 개를 같이 잰다.

- **천장**: 닫힌 클래스를 절반씩 나눠 두 평균을 같은 영역·같은 f로 비교. 같은
  음절을 두 번 잰 것이므로 코퍼스 자체의 잡음만 들어간다
- **불일치 대조**: 초성이 다른 열린 음절과 맞춰본 값, 즉 우연 수준

| | SERI95 (338쌍) | PE92 (1,996쌍) |
|---|---|---|
| 천장 (같은 클래스 반쪽끼리) | 0.980 | 0.971 |
| **일치 (압축 1개로 예측)** | **0.915** | **0.903** |
| 불일치 대조 (우연 수준) | 0.780 | 0.767 |
| 우연→천장 구간 중 회수한 비율 | **0.680** | **0.665** |
| 천장까지 남은 잔차 | 0.064 | 0.068 |
| 잔차 / 천장 표준편차 | 10.4σ | 7.7σ |
| 잔차가 개별적으로 3σ를 넘는 쌍 | **92.0%** | **76.5%** |

두 코퍼스가 같은 답을 준다. **압축 하나가 우연에서 천장까지의 약 2/3를
가져간다.** 동시에 잔차는 천장 표준편차의 8~10배이고, 그것이 소수 이상치
때문이 아니라는 것도 확인된다 — 쌍을 개별로 보아도 76.5%(PE92) / 92.0%(SERI95)가
자기 자신의 잡음 하한을 3σ 넘게 밑돈다.

압축 계수 스윕이 탐색 범위 끝에 몰려서 생긴 값도 아니다. 경계에 닿은 쌍은
2.4%(PE92) / 2.7%(SERI95)뿐이다.

답은 양자택일이 아니다.

> 종성이 붙을 때 일어나는 일의 대부분은 위쪽을 수직으로 누르는 것이고,
> 그것은 파라미터 하나로 잡힌다. 그러나 1/3은 눌림으로 설명되지 않는다.
> 자모는 역할에 따라 실제로 다시 그려진다.

## 5. 압축량은 상수가 아니라 중성 부류의 함수다

최적 압축 계수를 중성 부류별로 나누면 갈린다.

| 중성 부류 | SERI95 | PE92 | 예 |
|---|---|---|---|
| horizontal (ㅗㅛㅜㅠㅡ) | 0.668 | 0.682 | 곡, 문 |
| vertical (ㅏㅓㅣ 등) | 0.711 | 0.702 | 각, 반 |
| mixed (ㅘㅚㅢ 등) | 0.782 | 0.767 | 왕, 원 |

순서가 두 코퍼스에서 같다. 중성이 이미 아래를 쓰는 horizontal 부류에서 가장
많이 눌리고, 좌우로 벌어지는 mixed에서 가장 덜 눌린다.

이 값이 잡음이 아니라는 근거: 최적점 주변에서 코사인이 최적값 ±0.005 안에 드는
f 구간의 폭이 평균 0.056이다(스윕 격자 0.025). 즉 개별 쌍에서 압축 계수는 약
±0.03으로 식별되는데, 쌍 사이 산포는 0.55~0.85로 그보다 훨씬 넓다.

## 이 측정이 하지 못한 것

- **절대 크기·베이스라인·자간을 못 잰다.** 두 코퍼스 모두 문자 단위로 미리
  잘려 있어 페이지 문맥이 없다. HANDOFF Phase 4의 Global/Page 층
  (baseline, spacing, line drift)은 이 데이터로는 근거를 만들 수 없다.
  다른 데이터가 필요하다.
- **motor를 못 잰다.** offline 이미지뿐이다. HANDOFF §7이 금지한 대로 획 순서나
  속도를 역추정하지 않았다. 이 층은 AI-Hub 71307이 들어와야 열린다.
- **숫자/영문을 못 쟀다.** EMNIST(NIST)와 UJI(UCI)가 이 환경의 egress 정책에
  막혀 있다. HANDOFF §6의 shape family 재사용 질문은 아직 미측정이다.
- **자모를 직접 분할하지 않았다.** 4·5절은 음절 전체의 잉크맵 비교이지 자모
  세그먼테이션이 아니다. 자모 단위 shape 분포를 직접 보려면 분할이 필요하고,
  그것은 아직 없다.

## 재현

전체를 한 번에 돌리려면:

```bash
pip install -r requirements.txt
python scripts/download_public.py
python scripts/bootstrap_after_download.py
```

`bootstrap_after_download.py`는 입력이 없는 단계를 건너뛰고 마지막에
무엇이 돌았고 무엇이 왜 건너뛰어졌는지 출력한다. 막혀서 안 돈 단계와
통과한 단계가 같아 보이면 안 되기 때문이다.

단계별로 돌리려면:

```bash
python scripts/download_public.py --only hanguldb_git
python scripts/verify_dataset.py data/raw/PE92_train.zip data/raw/SERI_Test.zip

python scripts/extract_hgu1.py data/raw/SERI_Test.zip  --out data/extracted/seri95
python scripts/extract_hgu1.py data/raw/PE92_train.zip --out data/extracted/pe92 --drop-tail 5

python scripts/analyze_images.py data/extracted/seri95 --out data/features/seri95_shapes.csv
python scripts/pca_report.py data/features/seri95_shapes.csv --out reports/seri95_pca.json

python scripts/shape_space.py data/extracted/seri95 --out reports/seri95_shape_space.json \
    --classes 120 --modes-dir reports/modes/seri95
python scripts/basis_control.py data/extracted/seri95/UAC00_가 --out reports/seri95_basis_control.json
python scripts/jamo_context.py data/extracted/seri95 --out reports/seri95_jamo_context.json
python scripts/jamo_context.py data/extracted/pe92   --out reports/pe92_jamo_context.json
```

`--drop-tail 5`는 HangulDB README가 PE92의 오라벨 샘플이 파일 끝에 몰려 있다고
경고한 것에 대응한다.
